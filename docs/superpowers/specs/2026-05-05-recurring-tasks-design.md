# 周期任务与分钟级时间语义设计方案

## 1. 目标

本次改动新增一套与普通任务并列的“周期任务”子系统，用于管理按固定周期重复出现、需要填写进展的任务模板。

本次同时统一现有应用的时间语义：

- 存储、提醒、到期判定统一精确到分钟
- 列表筛选与概览统计允许继续按天聚合展示

## 2. 范围

### 2.1 纳入范围

- 新增周期任务模板、周期实例、进展记录三层模型
- 新增周期任务独立入口与基础管理界面
- 新增周期实例未提交提醒
- 统一现有普通任务时间显示与提醒文案到分钟级
- 为 SQLite、Tauri 命令层、前端状态层补齐对应结构和测试

### 2.2 不纳入范围

- 周期任务与普通任务建立关联
- 云同步、多端协作
- 日历视图
- 复杂自定义重复规则（如每月第三个周一）
- 周期任务附件、富文本编辑

## 3. 核心设计

### 3.1 独立子系统

周期任务不扩展现有 `TaskItem`，而是单独建模为独立领域，避免污染现有普通任务的完成、截止、提醒和筛选语义。

前端目录新增：

- `src/features/recurring`

后端 SQLite / Tauri 对应新增：

- `recurring_tasks`
- `recurring_periods`
- `recurring_progress_entries`

### 3.2 数据模型

#### `RecurringTask`

表示周期任务模板。

建议字段：

- `id`
- `title`
- `description`
- `cadence_unit`：`minute | hour | day | week`
- `cadence_interval`：正整数
- `remind_at_end`：是否在周期结束且未提交时提醒
- `is_active`
- `created_at`
- `updated_at`

#### `RecurringPeriod`

表示某个模板生成的一次周期实例。

建议字段：

- `id`
- `task_id`
- `start_at`
- `end_at`
- `closed_at`
- `created_at`
- `updated_at`

约束：

- 同一模板下周期实例按时间顺序连续生成
- 周期实例允许回看，不允许删除后重排历史

#### `RecurringProgressEntry`

表示某个周期实例下的一条进展记录。

建议字段：

- `id`
- `period_id`
- `content`
- `created_at`
- `updated_at`

规则：

- 同一周期允许多条进展
- 进展记录允许编辑
- 周期“已提交”状态通过是否存在进展记录推导，不单独存库

## 4. 业务规则

### 4.1 周期生成

- 创建周期任务模板时立即生成当前周期实例
- 当当前时间晚于当前实例 `end_at` 时，系统自动补齐后续周期实例，直到覆盖当前时间
- 补周期时不回填虚假的进展记录

### 4.2 提交判定

- 某周期实例下 `0` 条进展记录：未提交
- 某周期实例下 `>= 1` 条进展记录：已提交

### 4.3 提醒规则

- 模板启用提醒且当前周期结束后仍未提交时，进入提醒集合
- 同一个周期实例只对同一未提交状态发一次桌面提醒，状态变化后可重新进入提醒
- 提醒时间和现有任务提醒一样，底层统一按分钟计算

### 4.4 历史修改

- 已有进展记录允许编辑
- 编辑历史进展不会改变周期边界
- 补写历史周期进展是允许的

## 5. 时间语义

### 5.1 统一原则

- 数据库存储继续使用 ISO 时间字符串
- 所有新旧任务的时间比较使用完整时间戳，不再默认截断到日期
- UI 显示默认展示到分钟，例如 `YYYY-MM-DD HH:mm`

### 5.2 展示与统计

- 提醒、是否逾期、是否到期：按分钟判定
- “今天 / 未来 7 天 / 最近 7 天”一类概览仍允许按天聚合
- 也就是说：底层精确到分钟，概览可按天汇总

## 6. UI 落点

### 6.1 主入口

在顶部主操作区新增“周期任务”入口，与：

- `任务概览`
- `任务组管理`
- `新建`

并列出现。

### 6.2 主界面职责

周期任务入口承载：

- 周期任务列表
- 当前周期状态
- 进展记录查看与编辑
- 历史周期切换

### 6.3 概览摘要

`TaskOverview` 只补充周期任务摘要信息，例如：

- 待提交周期数
- 已逾期未提交周期数
- 最近新增进展数

不把周期任务主交互塞进概览。

## 7. 风险控制

- 不修改现有普通任务主模型，避免引入大面积条件分支
- 时间粒度升级时，区分“展示聚合”与“判定精度”
- SQLite 迁移必须幂等
- 周期补实例逻辑必须可重复执行且结果稳定

## 8. 实施顺序

1. 先补设计文档和实现计划
2. 先落 SQLite 表、迁移、Rust 模型与命令
3. 再落前端 recurring 领域、store 和 UI
4. 再统一现有普通任务时间显示与提醒逻辑
5. 最后补概览摘要、测试和文档收尾
